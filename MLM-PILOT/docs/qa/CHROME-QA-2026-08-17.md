## 1. How this was graded

The Browser pane was not compositing frames in this session, so no screenshot was
possible. Every visual claim below is therefore a computed measurement taken from
rendered pages in a real browser, not a reading of source. Contrast was computed from
`getComputedStyle`, compositing every translucent background layer down the ancestor
chain to the first opaque layer, resolving inherited element opacity, and averaging the
colour stops of any opaque gradient background.

Two measurement errors of my own were caught and corrected before anything was
reported, and they are recorded here so the numbers can be trusted:

1. **Transition lag.** Flipping `data-theme` and reading immediately returns
   mid-transition colours. A first pass produced ratios of 1.10 to 1.69 on
   `faq.html` and `conductor.html` that were pure artefact. Every figure in this
   report comes from a page **loaded fresh with the target theme already in storage**
   and read after a settle delay.
2. **Gradient blindness.** An early pass ignored `background-image`, which made the
   bank-connect dialog on `shop.html` look catastrophic (title at 1.65 to 1, progress
   labels at 1.21 to 1). The dialog card is painted by an opaque white gradient. With
   gradients resolved, the same elements measure 17.45 and 12.66. **Those early
   figures are withdrawn and are not findings.**

Disabled controls are excluded from the pass or fail decision, per WCAG SC 1.4.3,
but are reported where measured.

## 3. Findings

### MEDIUM

**M1. The bar's item list is shared but its stylesheet is not, and the Plan page already
looks different. Pages: comp-plan.html primarily, conductor.html structurally.**

The markup is unified by `_partials/nav.html` and the build lint, and the behaviour is
unified by `site-chrome.js`. The chrome's **presentation** is still hand-rolled in four
separate places:

| Page | Where the navigation CSS comes from |
|---|---|
| index, shop, product, team, faq | `css/corporate.css` |
| library, library-agent | `css/library.css` |
| comp-plan | its own inline `<style>` block, no shared stylesheet at all |
| conductor | its own inline `<style>` block, no shared stylesheet at all |

`comp-plan.html` and `conductor.html` each define `.nav-links`, `.nav-link`,
`.nav-link.is-active`, `.nav-link.is-soon`, `.nav-signin`, `.nav-theme` and its
focus ring inline, in full.

Measured consequence today, at 1280 pixels wide:

| Page | Navigation font | Item gap | Header height | Navigation width |
|---|---|---|---|---|
| index, conductor, team, faq | 13.44 px | 26 px | 69 px | 898 px |
| library, library-agent | 13.44 px | 24 px | 69 px | 878 px |
| shop, product | 13.44 px | 26 px | 105 px | 953 px with cart |
| **comp-plan** | **12.80 px** | **20 px** | **65 px** | **796 px** |

At 390 pixels wide the difference is not subtle. Eight pages centre a 335 pixel bar
across the screen. `comp-plan` packs the same items left-aligned into a 181 pixel block
that starts at x=166 and wraps into four cramped rows, because its inline copy sets
`justify-content: normal` where the shared sheet sets `center`.

Nothing is hidden and nothing overflows, so this is not a broken bar. It is the same
bar rendered at a different size, spacing and alignment on one of the nine pages, which
is precisely the complaint that produced this contract. `conductor.html` currently
measures identical to index, which is the more worrying half: it matches today, by
hand, with nothing enforcing it. Contract section 4 says a build that cannot drift is
worth more than a navigation that is correct today, and no lint covers CSS drift.

*Recommended:* have `comp-plan.html` and `conductor.html` consume the shared chrome
rules instead of copying them, or at minimum bring comp-plan's font size, gap and
mobile justification into line, and extend the lint to the chrome CSS.

**M2. The Support button's open path cannot be evidenced, and it gives the user nothing
back if it fails. Pages: all nine.**

What was proven: the trigger exists on all nine, the handler is wired on all nine (a spy
on the vendor's `open` call fires exactly once per click on every page), the vendor
loader and configuration script are each loaded exactly once per page, and no inline
copy of the widget survives anywhere.

What could not be proven: that a chat window actually appears. On every page the vendor
container renders at zero height, `webchat:ready` never fired within 12 seconds, and
calling the vendor's own `open()` directly did nothing. **The pre-commit baseline
behaves identically**, so this is an environment limitation, not a regression this
commit introduced. It does mean the acceptance line "the support button works on all
nine" is graded on wiring, not on an opened chat.

There is also an unproven failure path worth closing. In `site-chrome.js`, `openNow()`
returns true as soon as `window.botpress.open` is a function. That function appears
about 383 milliseconds after load, well before the widget reports ready. If the vendor
proxy does not queue a pre-ready call, a click in that window is swallowed, the
deferred-open fallback is never armed because `wantOpen` is never set, and the button
gives the reader no feedback at all.

*Recommended:* arm the deferred open whenever the widget has not reported ready, rather
than trusting the presence of the function, and give the button a visible pending state
so a slow or blocked widget is never a silent refusal. Before deploy, one person should
open one page in a visible browser and click Support once.

**M3. The round's disclosed list of deliberately dark surfaces omits the largest one.
Pages: all nine.**

The commit record states the deliberately dark surfaces inside the light theme as
"each documented where it lives: the starfield hero, the bank-approval bar, and the
wallet and brand tiles."

Measured: **the navigation bar and the footer also stay dark in the light theme on all

the round's own summary of exceptions. Anyone reading the record would not know that
choosing light leaves the bar and the footer dark.

*Recommended:* add the chrome bar and the footer to the contract's named exceptions and
to the round's record. No code change needed.

## 5. Ruling on the Google Pay letter G

**Measured independently, not taken from the builder.** `#4285F4` on the tile's
`rgb(248,250,252)` computes **3.41 to 1**. The word "Pay" beside it, `rgb(32,33,36)` on
the same tile, computes **15.38 to 1**. The proposed alternative `#1558C0` computes
**6.29 to 1**. All three of builder B's figures are correct.

**Ruling: accepted as it stands. Not on the argument builder B made.**

The brand-logotype exemption in WCAG SC 1.4.3 does not apply here. That exemption covers
a logotype. This is not the Google Pay logotype: it is page text, the letters G and Pay
set in the site's own typeface at weight 800. Calling site text a logotype would let any
element opt out of contrast by asserting a brand, and that argument should not go on the
record as accepted.

It is accepted for three reasons that do hold:

1. The mark functions as an icon, not as text conveying information. It is
   `aria-hidden="true"`, so no assistive technology reads it. The governing criterion
   for a graphical object is SC 1.4.11 non-text contrast at 3 to 1, and 3.41 clears it.
2. The tile's accessible name is independent of the glyph. A sibling screen-reader-only
   span carries "Google Pay". Nothing about identifying or operating the tile depends on
   resolving the G.
3. The information survives without the glyph. The word "Pay" beside it reads at 15.38,
   the tile sits between Apple Pay and PayPal, and no user who cannot resolve the blue G
   loses the ability to identify or use the control.

**Two conditions attach.** First, record the reasoning in `shop.css` beside the
`.g-blue` rule, in the same measured style as the rest of that sheet, naming 3.41,
naming SC 1.4.11 as the criterion it is judged against, and explicitly stating that the
logotype exemption was considered and rejected. An exception that is not written down is
an exception that gets re-litigated. Second, take `#1558C0` at 6.29 the next time the
tile is touched. It is recognisably Google blue, it clears the text floor outright, and
it ends the argument permanently. That is a cleanup, not a blocker.

This is a LOW finding. It does not hold the gate.

## 8. New standing checklist rows earned by this pass

Added permanently, per the rule that every miss makes the checklist longer.

- **Shared markup is not shared chrome.** When a round unifies a component's markup,
  grade whether its CSS is also single-sourced. List every stylesheet and inline
  `<style>` block that defines the component's rules, and measure the component's
  rendered font size, spacing, box and mobile alignment on every page. Identical markup
  rendering at different sizes is still the bar changing between pages. This pass found
  four separate definitions of one navigation.
- **Measure after the transition settles, and load the theme rather than forcing it.**
  Flipping `data-theme` and reading immediately returns mid-transition colours and
  invents defects that are not there. Load each page with the target theme already in
  storage.
- **Resolve gradient backgrounds before claiming a ratio.** An element whose painted
  backdrop is a `background-image` will be measured against the wrong colour if only
  `background-color` is walked. Either resolve the gradient stops or mark the pair
  unresolved. Never report a ratio computed against a backdrop that is not what paints.
- **A wired handler is not a working feature.** When a third-party widget cannot be seen
  to open, say so and name the one-minute human check, rather than passing the row on
  the handler firing.
- **Grade the disclosed exception list against the measured one.** Sweep for every
  surface that does not change with the theme and check each against what the round said
  it was keeping dark. The biggest exception is the one most likely to go unmentioned.

## D7. New findings this pass

### LOW

**N1. `aria-current="page"` on a link that does not point at the current page. Pages:
`faq.html` (new this commit) and `product.html` (pre-existing, missed in my first pass).**

`faq.html` marks Learn active, and Learn points at `index.html`. `product.html` marks Shop
active, and Shop points at `shop.html`. Both carry `aria-current="page"`. The visual
highlight is right in both cases, and the contract's own registry deliberately maps these
two pages to a section rather than to themselves, which is the sensible reading of "its own
item" for a page with no item in the bar. But a screen-reader user on the Frequently Asked
Questions page hears "Learn, current page" while reading a different page. `page` names the
link representing the current page; for a section-level highlight `aria-current="true"` is
the accurate token.

Not a regression in substance: `product.html` behaved this way before this round and
`faq.html` previously had no active item at all, which was worse. Fix is one attribute on
two pages, plus parameterising the expected token in the lint alongside the expected href.
Does not hold the gate.

**N2. The wall-clock deadline is correct, but it is only *checked* when the poll fires.
File: `js/site-chrome.js`.**

The arithmetic fix is right and I confirmed it. The remaining characteristic is that
`Date.now() >= deadline` is evaluated inside the 250 millisecond interval, and a browser
throttles that interval in a hidden or backgrounded document. Observed directly: in an
off-screen sandboxed frame the transition to `unavailable` had not fired within 40 seconds,
while at top level it fired at 16.7 seconds.

This is not the old bug and not user-visible harm. A reader in a background tab is not
waiting on the button, and when they return the timer un-throttles and the next tick
applies the deadline at once. Recording it so the 15 second figure is not later read as a
guarantee in a background tab. If it is ever worth hardening, evaluate the deadline on
`visibilitychange` as well as on the tick. Does not hold the gate.

The chat vendor injects a Google Fonts stylesheet
(`https://fonts.googleapis.com/css2?family=inter...`) into the document at runtime. It is
not in any page's markup, it appears only after the vendor loader runs, and it is unchanged
by this round. Out of scope for a chrome gate; noted so it is on the record as a
third-party external request the property makes.

## D11. New standing checklist rows earned by this pass

- **A probe that can land on a state-dependent variant must exclude that state.** Selecting
  a navigation link by its `href` lands on the active item on the page that owns that href.
  Measure plain and active variants separately, or a highlight will be reported as drift.
  This is the L1 error, and it cost the builders a round trip to refute.
- **When a fix tightens spacing, re-run hit testing and target size, not just appearance.**
  A 26 to 16 pixel gap change is a target-spacing change. Check the spacing exception at
  every width where the bar wraps.
- **Rule on a permitted difference by asking whether the styling differs or the same
  styling is reflowing.** Identical font, gap, justification, order and wrap rule with a
  different wrap point is one stylesheet behaving; different values for the same property
  is drift. Bisect the viewport width to state the band rather than naming two widths.
- **Test a timeout by making the dependency genuinely unreachable, and say exactly what you
  changed to do it.** Two URL constants repointed at a dead port is a fair test; anything
  touching the logic under test is not.
- **Re-run a full sweep when the stylesheet that produced the earlier numbers is deleted.**
  A delta gate may skip rows it proved clean, but not rows whose evidence lived in a file
  that no longer exists.
