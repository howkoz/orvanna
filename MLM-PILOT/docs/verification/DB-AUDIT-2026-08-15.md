### 2.3 Recorded and applied, but the live result does not match the recorded intent

| Ledger version | Recorded intent | Live reality |
|---|---|---|
| `20260815175105` (013) | `create index ... demo_orders_created_at_idx on app.demo_orders (created_at desc)` | Index exists on `(created_at)` ASCENDING, created by migration 010. The DESC index was never built. **F2.** |

This is the sloppiest thing in the database, and it is worth being precise about
why it does not matter for speed and does matter for the record.

It does not matter for speed. A Postgres btree can be walked in either
direction. The recent-orders query proves it:

```
Limit  (cost=0.14..3.80 rows=25) (actual time=0.028..0.102 rows=25)
  ->  Index Scan Backward using demo_orders_created_at_idx on demo_orders
```

`Index Scan Backward` is the planner using the ASCENDING index to satisfy
`order by created_at desc`, at a total cost of 3.80. A dedicated DESC index
would have bought nothing. Migration 013's comment block is a well-argued case
for an index that migration 010 had already built the day before.

It does matter for the record. The ledger now asserts a DDL statement whose
effect is absent from the database. Anyone rebuilding from the ledger, or
reading it to answer "what indexes do we have", gets a wrong answer. And the
`if not exists` guard that made this silent would do the same thing again on the
next same-named index.

Recommended (not applied): retire 013 with a short file in `db\migrations\`
recording that it was a no-op and why, so the repository and the ledger tell the
same story. Do NOT drop and rebuild the index as DESC; there is nothing to gain.

## 4. Migration 014 in detail

### 4.1 The constraint change

Applied and correct. Live:

```
demo_users_role_check  CHECK ((role = ANY (ARRAY['admin'::text, 'staff'::text, 'member'::text])))
```

Migration 012 created it inline as `check (role in ('admin','staff'))`, which
Postgres auto-named `demo_users_role_check`, and 014 dropped that exact name and
replaced it. The name guess was right.

One flaw: `alter table app.demo_users drop constraint demo_users_role_check;`
has no `if exists`, so migration 014 cannot be run twice (F9). The charter asks
for idempotent where possible, and here it was possible. Steps 2, 3 and 4 all
guard themselves (`add column if not exists`, `where not exists`, `revoke`).

### 4.2 The added column

```
member_code   text   nullable   no default   no index   no foreign key
```

Nullable is correct: the admin and staff accounts are not members and carry
null. No index is fine because nothing queries by it; `demo-login` looks up
`lower(username)`, and `create-payment` resolves the code against `app.members`,
not against `app.demo_users`.

### 4.3 Should member_code be a foreign key? Yes.

`app.members.member_code` carries a UNIQUE constraint
(`members_member_code_key`), so it is a legal FK target. Adding
`references app.members(member_code)` costs nothing and buys the guarantee that
1,000 sign-in accounts cannot drift away from the roster they claim to
represent. Without it, a member row could be recoded or removed and 1,000
accounts would quietly point at nothing.

Today the data is clean, verified:

| Check | Result |
|---|---|
| Members | 1,000 |
| demo_users rows | 1,002 (1,000 member, 2 admin/staff) |
| Member accounts with a null member_code | 0 |
| Member accounts whose member_code has no matching member | 0 |
| Members with no sign-in account | 0 |
| Accounts where username differs from member_code | 0 |

Recommended (not applied): add the FK. It is a one-line migration and the data
already satisfies it.

### 4.4 Does the unique index still hold? Yes, both of them.

Two uniqueness guarantees exist on `demo_users` and both survived the 1,000-row
insert:

- `demo_users_username_key` UNIQUE (username), case sensitive, from migration 012
- `demo_users_username_lower_key` UNIQUE (lower(username)), case insensitive, from migration 012

1,002 rows are present, so both indexes accepted every insert. The insert's own
guard (`where not exists (select 1 from app.demo_users u where lower(u.username)
= lower(m.member_code))`) matches the case-insensitive index exactly, which is
why it did not collide. Member codes are uppercase and structurally distinct
from the two admin/staff usernames, so there was never a near miss.

The `demo-login` lookup uses `lower(username) = lower($1)`, which matches the
functional index term for term and so uses it.

### 4.5 The shared bcrypt hash, stated plainly

All 1,000 member accounts share one bcrypt hash of one password,
`OrvannaDemo2026`, printed on the checkout page on purpose.

The consequence worth stating: **knowing the password for one member account is
knowing it for all 1,000**. There is no per-member secret. Anyone who reads the
page can sign in as any member code in the roster, and the roster itself is
public through `v_demo_members`. So "signing in as a member" is not
authentication in any meaningful sense; it is a public selector with a
ceremonial password in front of it.

For this demonstration that is the correct trade and the migration says so. Two
things keep it safe:

1. A member account cannot reach the member portal or the staff console. Those
   demand role `admin` and `staff`, and the server-side gate returns
   `wrong_role`. Verified in `demo-login\index.ts`: the role comparison happens
   after the credential check and before anything is returned.
2. The only thing a member account unlocks is data that `v_demo_members` already
   publishes to the anonymous public.

The one thing to keep true as the project grows: **nothing private may ever be
placed behind the member role.** The moment a member-role page shows anything a
stranger should not see, this shared hash becomes a real vulnerability rather
than a deliberate demo convenience. That is a design constraint to carry
forward, not a defect today.

Second, smaller note: the single hash is also a single rotation point. Changing
the demo password is one UPDATE across 1,000 rows, which is convenient, but it
also means there is no way to revoke one account.

## 5. Indexes and query cost on the hot path

All four hot-path statements were traced with EXPLAIN ANALYZE against live data.

### 5.1 Daily circuit-breaker count on demo_orders. PASS.

Query (`create-payment` line 283), run on every single call:

```sql
select count(*)::int from app.demo_orders where created_at >= date_trunc('day', now())
```

```
Aggregate  (cost=7.54..7.55 rows=1) (actual time=0.074..0.080)
  ->  Index Only Scan using demo_orders_created_at_idx on demo_orders
        Index Cond: (created_at >= date_trunc('day', now()))
```

An **Index Only Scan**, the best available plan: the count never touches the
heap for the predicate and reads only one day's slice regardless of how many
orders accumulate. This is the thing migration 013 set out to fix, and it was
already fixed by migration 010.

### 5.2 Rate-limit lookup on demo_rate_events (ip_hash, window_start). PASS.

```
Index Scan using demo_rate_events_pkey on demo_rate_events
  Index Cond: ((ip_hash = 'x') AND (window_start = date_trunc('minute', now())))
```

Exact PK hit. The hourly variant (`ip_hash = $1 and window_start > now() -
interval '1 hour'`) is a range scan on the same PK with `ip_hash` as the leading
equality column, which is the textbook use of a composite index. The upsert
(`on conflict (ip_hash, window_start)`) uses the same index. Nothing to add.

### 5.3 Member lookup by member_code. PASS.

`select id from app.members where member_code = $1` hits
`members_member_code_key`, a unique btree. Single-row lookup at any table size.

### 5.4 Recent-orders list ordered by created_at. PASS.

```
Limit  (cost=0.14..3.80 rows=25) (actual time=0.028..0.102)
  ->  Index Scan Backward using demo_orders_created_at_idx on demo_orders
```

Backward walk of the ASC index, 25 rows, cost 3.80. Does not grow.

### 5.5 The one that WILL grow without bound: the abandon sweep. FAIL. (F4)

Query (`_shared\edge.ts` line 680):

```sql
select order_number, total_cents, payment_reference
  from app.demo_orders
 where payment_status in ('created','processing')
   and created_at < now() - interval '1 hour'
 order by created_at asc
 limit 50
```

```
Limit -> Sort -> Seq Scan on demo_orders
  Filter: ((payment_status = ANY ('{created,processing}')) AND (created_at < now() - '01:00:00'))
  Rows Removed by Filter: 65
```

A full sequential scan plus a sort. At 81 rows that is free. The problem is what
happens as the table grows, and it is worse than it first looks, because the
obvious alternative plan is also bad.

If the planner switched to walking `demo_orders_created_at_idx` ascending to get
the `order by` for free, it would start at the OLDEST rows, and the oldest rows
are precisely the ones already resolved to `succeeded`, `failed` or `abandoned`.
It would have to skip past every historical terminal row before finding 50 live
candidates. Both plans therefore scan a set that grows with total order count,
while the answer being sought is always a small, recent, non-terminal set.

The correct fix is a partial index that indexes only the rows the sweep can
possibly want:

```sql
create index demo_orders_sweep_idx
  on app.demo_orders (created_at)
  where payment_status in ('created', 'processing');
```

This index contains only non-terminal orders, so it stays small forever: rows
leave it automatically when they settle. It satisfies the filter, the ordering
and the limit in one ordered scan of a set bounded by concurrent in-flight
traffic rather than by lifetime volume. Not applied; this is a read-only audit.

The existing `demo_orders_payment_status_idx` is a poor substitute: two of its
five values (`created`, `processing`) are the common ones early in a row's life,
so its selectivity is weak and it carries no ordering help.

### 5.6 Also unindexed: the rate-ledger cleanup. (F7)

```sql
delete from app.demo_rate_events where window_start < now() - interval '24 hours'
```

The PK `(ip_hash, window_start)` cannot serve a predicate on `window_start`
alone, because `ip_hash` leads. This is a sequential scan of the whole ledger,
fired on roughly 2 percent of rate-limited calls. At 107 rows it is invisible.
It grows with the number of distinct visitor IP addresses per day, so a
publicity spike is exactly when it gets slow. A plain index on `(window_start)`
would fix it, at the cost of one more index to maintain on a write-heavy table.
Given the 24-hour retention this is a judgment call, not an obligation; the
table is self-limiting as long as the cleanup keeps firing.

### 6.3 The demo_orders status transition guard. Correct and complete.

`app.demo_orders_guard_status_transition()` fires BEFORE UPDATE OF
payment_status and enforces four rules:

1. Same status in, same status out: allowed (idempotent retry).
2. `succeeded` and `failed` are terminal: no exit.
3. `abandoned` may resolve only to `succeeded` or `failed`.
4. Nothing may return to `created`.

That is a well-formed state machine with no hole I could find. A companion
trigger, `demo_orders_touch_status_updated_at`, stamps `status_updated_at` only
when the status actually changes (`is distinct from`), so an unrelated column
update does not falsify the timestamp. Confirmed by the zero rows where
`status_updated_at < created_at`.

The sponsor-cycle trigger on `app.members` is also sound: it rejects
self-sponsorship, walks the upline, and carries a one-million-step circuit
breaker so a pre-existing cycle raises an error rather than hanging.

### 6.4 Can the abandon sweep strand a row? YES, and it is stranding rows now. (F3)

Live counts, 2026-08-15:

| payment_status | rows | older than 1 hour | payment_reference present |
|---|---|---|---|
| created | 26 | **13** | 26 |
| succeeded | 23 | 16 | 23 |
| abandoned | 21 | 21 | 21 |
| failed | 8 | 8 | 8 |
| processing | 3 | **3** | 3 |

Sixteen rows are past the one-hour abandon window and have not aged out. The
spec (section 5.4) says a row stuck at `created` or `processing` for over one
hour becomes `abandoned`. Sixteen rows say otherwise.

The cause is throughput, not logic. Three things throttle the sweep:

1. It has exactly one caller, `list-demo-orders`. If nobody loads the
   live-orders section, the sweep never runs at all. There is no scheduler.
2. That caller gates it on `Math.random() < 0.25`, one call in four.
3. Each run rechecks at most 5 rows (`maxRetrieves: 5`).

Effective throughput is about 1.25 rows per page load of the live-orders
section. A backlog of 16 needs roughly 13 such loads to clear, and only if
HyperSwitch answers every retrieve.

Two additional stranding paths, both real:

**Path A, the processor is unavailable.** `retrieveAndApplyPaymentTruth` returns
`not_configured` when `HYPERSWITCH_API_KEY` is absent, and `processor_unreachable`
on a network failure. In both cases the sweep does `continue` and leaves the row
alone, correctly ("an unanswered question is not an abandonment"). But those
rows keep their place at the FRONT of the candidate query, which is
`order by created_at asc limit 50`. If 50 or more such rows accumulate, they
form a permanent head-of-line block and no newer row is ever examined again.
The sweep would silently stop working while appearing to run.

**Path B, abandoned is a one-way door for the shopper.** A slow 3DS challenge
can outlive the hour. The sweep ages the row to `abandoned`. The shopper then
finishes at the bank and the site calls `confirm-payment`, which does NOT pass
`allowResolveFromAbandoned`, so its guarded UPDATE
(`where payment_status in ('created','processing')`) matches nothing. The row
stays `abandoned` forever even though HyperSwitch says `succeeded`. Only
`payment-webhook` can rescue it, and only if webhooks are configured at
HyperSwitch. This is F8.

Worth noting in the sweep's defence: the design is deliberately conservative in
the right direction. Rows with no `payment_reference` age out immediately
because there is nothing to ask about; rows with a reference are re-retrieved
before being aged; and the final UPDATE repeats the status condition so a row
that settled mid-sweep is not disturbed. The engineering is careful. The problem
is that a careful sweep with no scheduler is a sweep that does not run.

Recommended (not applied), in order of value:

1. Give the sweep a real trigger. A Supabase scheduled function, or at minimum
   also call it from `create-payment`, so it does not depend on someone looking
   at the live-orders list.
2. Change the candidate ordering, or exclude rows whose last retrieve failed, so
   an unreachable processor cannot head-of-line block the queue.
3. Decide deliberately whether `confirm-payment` should be allowed to resolve
   `abandoned` into `succeeded`. The database already permits that transition;
   only the function refuses it. Since `confirm-payment` believes only
   HyperSwitch's own answer, allowing it would not weaken the trust model.
