ORVANNA sandbox test cards

Current as of 2026-08-16. The live processor behind the orvanna.io checkout and the staff call console is the Braintree sandbox, reached through HyperSwitch, live since 2026-08-15. This is a sandbox: no real money moves, ever. The numbers below are industry-standard test cards, public knowledge, and safe to share, print, or store openly. Every behaviour on this page was run end to end on the live rail, not copied from a vendor page.
Acronym key. 3DS is 3-D Secure, the card-network check that asks the card's issuing bank to confirm the shopper really is the cardholder; when it fires, a bank approval screen appears in the checkout. PAN is Primary Account Number, the long number on the front of a card. CVV is Card Verification Value, the short code on the back.
Expiry and security code: use expiry 01 / 29 on every test card; that is the expiry the verified runs used on this rail. Security code: any 3 digit value, for example 123. Cardholder name can be anything.

The amount rule. Braintree's sandbox declines by AMOUNT as well as by card: any charge between 2000.00 and 3000.00 dollars declines, whatever card is used. If a cart in that range fails, it is this rule, not the card. Keep success demos under 2000.00 dollars.
Where the challenge comes from. The approval screen on 4111 1111 1111 1111 is served by Braintree's own 3DS in the sandbox. It is a genuine challenge flow: the payment parks at requires_customer_action while the shopper is in front of the screen, and completes only after the approval.

What no longer applies

4000 0000 0000 0002 was the decline card on the RETIRED simulator rail (the HyperSwitch dummy connectors, switched off 2026-08-15 when Braintree went live). It no longer plays that role here; use 4000 1111 1111 1115 to demonstrate a decline.

3DS test cards from other vendors' documentation do not apply here. The 3DSecure.io sandbox PANs and the Stripe 3DS card list in the superseded section below belong to authentication paths that are not the live rail. On the current rail the challenge is Braintree's, and 4111 1111 1111 1111 is the challenge card.

Superseded 2026-08-16: the pre-Braintree card worlds (history only)

Everything below documents the rails that were live BEFORE 2026-08-15: external authentication through 3DSecure.io, the Stripe fallback path, and the HyperSwitch dummy connectors. All three are retired or parked. None of these matrices decide anything on the current rail, and two rows aged badly enough to invert: the old "cards that succeed with no approval screen" section listed 4111 1111 1111 1111, which is now the card that DOES show the approval screen, and the old decline section led with 4000 0000 0000 0002, which is no longer the decline card. Kept for history and for the day a rail below comes back.

Historical acronym key. ACS is Access Control Server, the issuing bank's server that draws the approval screen. transStatus is the single letter 3DS uses to report how the check went: Y authenticated, N not authenticated, A attempted, R rejected by the issuer, U unavailable, I informational.
Historical expiry guidance: any FUTURE expiry date (for example 12 / 30) and any 3 digit CVV, for example 123. American Express uses a 4 digit code. Cardholder name can be anything.
Read this before you pick a card. There are three separate worlds of test cards here and they are NOT interchangeable. Mixing them is the fastest way to lose an afternoon. Which world you are in depends on who is doing the authentication:
  • External authentication (3DSecure.io), the path this site used. Use the 3DSecure.io PANs below. This was the primary matrix.
  • The processor's own 3DS (stripe_test), the fallback path. Use the Stripe cards.
  • The dummy connector (pretendpay). Use the HyperSwitch dummy list.

1. Primary matrix: 3DSecure.io sandbox PANs

3DSecure.io does not publish a flat card list. It publishes an encoding scheme: the outcome is chosen by the LAST FOUR DIGITS of the card number, and the leading digits are free. Any last four that does not match a defined case returns an error. This was the authentication path the Orvanna checkout used, so these were the cards that decided whether an approval screen appeared.

The trap in this section. These are 3DSecure.io sandbox numbers, not processor test-mode numbers. The authentication leg can pass against 3DSecure.io and the AUTHORIZATION leg can then fail, because the processor's test mode does not recognize the card. If that happens the code is not broken: the test proved authentication only. Route these to the dummy connector, or read the outcome as an authentication result rather than an end-to-end sale.
What the approval screen looks like. For the automatic cases (last four xx70 and xx71) the screen submits itself with JavaScript, so on screen it is a brief flash and the tester types nothing. For the manual case (xx72) the screen must be completed by hand; the exact wording and controls are not published. When you run xx72 for the first time, screenshot it and write the answer in here.

The two rows that matter most for wording. 4000 0084 0000 1629 is the case where the shopper does everything right and still gets a no: the bank confirms who they are, then refuses the money. That decline must never read like a plain decline, and telling that shopper to "check their card details" is actively wrong. 4000 0084 0000 1280 is the case where the security check itself breaks, which is nobody's fault and must not blame the card.

4242 4242 4242 4242 CAN NEVER SHOW AN APPROVAL SCREEN. It is documented as a card that supports 3DS but is not enrolled in it, so no matter what the site asks for, no screen appears. If you test "is 3DS working?" with this card, the answer will always look like no, and it will be wrong. This exact confusion is what sent us down a long road once already. Use a card from section 1 to see an approval screen; use this one to prove the frictionless path still sails through.
American Express 3782 8224 6310 005 does not support 3DS at all and cannot be asked to. It is the card that proves the flow degrades gracefully when an approval is simply impossible.

The published dummy connector list has exactly ONE 3DS card, a success card, and no 3DS failure card. If you need an approval that fails on the dummy connector, it is not published; use section 1 instead.

Dummy connector quirks worth knowing: payments made through dummy connectors expire after 2 days, and dummy connectors support payments and refunds only. Perfect for a demo, useless for theft.
One thing that is NOT a knob. The acquirer BIN (Bank Identification Number) configured with the authentication provider, 424242 in our sandbox, says WHO IS ASKING: which acquiring bank and which merchant account. The card number says WHO IS PAYING, and only the card number decides whether an approval screen appears. The acquirer BIN is the same on every transaction forever, and nothing you type into it will turn approvals on or off. It merely happens to look like the start of the famous test card, which is exactly the coincidence that makes it confusing.
