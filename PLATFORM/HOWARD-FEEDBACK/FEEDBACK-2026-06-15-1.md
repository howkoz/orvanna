# Independent Gaps - Orvanna

Created: 2026-06-15  
P0 - I Would Not Pitch Hard Until These Are Fixed

| Gap | My feedback | What would satisfy me |
|---|---|---|
| Token portability is still the main unresolved bet | The project currently talks like portable network tokens are achievable, but the business only works if the token is issued under the merchant's or neutral TSP's control, not a processor TRID. This cannot stay as a nice assumption. | A proof file showing the exact vault/TSP path, TRID owner, Visa support, Mastercard support, target-processor acceptance, fees, and fallback behavior. |
| PCI wording is too comfortable | The docs say Orvanna does not store PAN, but they also say Orvanna asks the vault for PAN fallback. If any Orvanna component can retrieve, pass, proxy, or forward PAN, PCI scope still matters. "Lighter scope" may be true, but "light PCI scope" is too casual until the data path is drawn. | A PAN fallback architecture choice: vault proxy, direct retrieval, secure relay, or no PAN fallback. Then update the PCI model to match. |
| The competitive set is too narrow | The four-vendor comparison is useful but not enough for a 2026 investor claim. Yuno, IXOPAY/TokenEx, BR-DGE, CellPoint Digital, APEXX, Payrails, Paydock, and others may already claim pieces of this stack. | A competitor matrix that marks each pillar as proven, claimed, weak, unknown, or not offered, with source links. |
| The "nobody sells all eight" claim is too strong right now | It may be true, but I would not let Howard say it yet. The claim invites an investor to name one competitor and knock the pitch sideways. | Change language to "we have not found one vendor that combines all eight in this exact ownership model" until the competitor matrix is done. |
| The business may accidentally become a HyperSwitch wrapper | If the build is HyperSwitch core plus HyperSwitch Control Center plus managed connectors, Orvanna's product boundary must be sharper. Otherwise the question becomes: why not just use HyperSwitch/Juspay? | Define what Orvanna owns beyond HyperSwitch: token strategy, honest retry layer, operating model, vault/TSP integration, pilot package, or vertical specialization. |
| Managed-first conflicts with ownable-later | The current story says rent first, own later. That is fine, but if key connectors only exist in managed Cloud, the ownership promise weakens. | A transition plan showing which components are rented, which are owned, when they move, and what remains vendor-dependent. |
| The first pilot is not narrow enough | "Core + one connector + external vault + 3DS + console" is still big. If the first proof tries to show everything, it can stall. | A pilot slice with one market, one processor, one vault path, one payment type, one success metric, and one rollback plan. |
| Cost and staffing are not optional details | The docs name 24/7 upkeep, but the model is not honest until it prices on-call, compliance, connector certification, support, incident response, and cloud cost. | A cost/team model with named roles, monthly run cost, build cost, and minimum viable operations team. |

## P1 - I Would Challenge These Before Build Planning

| Gap | My feedback | What would satisfy me |
|---|---|---|
| Payment lifecycle is too synchronous | Real payments have webhooks, delayed captures, async 3DS, processor timeouts, reversals, duplicate callbacks, and pending states. The current flow is clean, but too straight-line. | Add an async event model: webhook handling, pending states, duplicate event handling, retries, idempotency, and final-state rules. |
| Reconciliation is mostly absent | An orchestrator that routes auths, captures, refunds, and voids needs a way to reconcile attempts, captures, refunds, disputes, and processor reports. Even if Orvanna is not the ledger, it needs traceability to money movement. | Add a reconciliation/settlement visibility model or explicitly declare it out of scope for the first pilot. |
| Decline classification is under-modeled | "Soft" and "hard" are right concepts, but processor codes differ. A wrong map can waste fees or stop recoverable payments. | A decline-code normalization matrix by processor, with token-specific declines separated from issuer declines. |
| Honest retry depends on upstream subscription data | Orvanna cannot know a subscription is dead unless the merchant sends subscription status, failed-streak count, and maybe customer lifecycle data. | Define the merchant input contract: required fields, optional fields, and what Orvanna can do without them. |
| Operator console guardrails need more depth | A no-code console can create outages if operators can change routing too freely. The current guardrails are a start, not enough. | Add approval workflow, preview impact, rollback, rule versioning, audit, permission tiers, and emergency freeze. |
| 3DS model is too shallow for a payment-grade plan | It says pluggable 3DS, but does not yet model CIT vs MIT, exemptions, liability shift evidence, challenge failure, abandoned challenge, regional mandates, or stored credential indicators. | Add a 3DS decision matrix and authentication-result data contract. |
| Vault neutrality may be commercially hard | "Neutral vault/TSP" is the right architecture, but vendor availability, onboarding time, network certification, and fees may be hard. | A vault vendor shortlist with capabilities, TRID model, fees, processor compatibility, regions, and PCI responsibility. |
| Regional strategy needs legal proof | Korea is treated as the obvious local-node case. That might be right, but it needs current legal, processor, vault, and latency evidence. | A Korea fact pack with law, data classes, vault options, local PSP path, latency hypothesis, and cost. |
| Connector certification is underpriced as a repeatable job | The adapter pattern makes the work bounded, not small. Each connector still has edge cases, certification, support, and processor changes over time. | Per-connector effort bands: easy, medium, hard, with certification steps and ongoing maintenance cost. |
| Fraud boundary needs sharper inputs | The docs say Orvanna is not a fraud engine. Good. But routing and 3DS decisions still need risk inputs. | Define the risk-provider interface or merchant risk-input fields. |

## P2 - I Would Clean These Up So The Work Does Not Get Sloppy

| Gap | My feedback | Fix |
|---|---|---|
| Some statements read as facts before proof | The docs sometimes say "will" when they should say "design goal" or "assumption." | Label claims as proven, assumption, design goal, or open question. |

| Demo polish could outrun proof | The HTML demos are useful, but polished visuals can make an unproven claim feel settled. | Keep demos behind the proof docs, not ahead of them. |
